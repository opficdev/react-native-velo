# 플랫폼별 이벤트 처리 방식 분리

README 핵심 성과 1번의 측정 기록

## 용어

- B: 라이브러리 없이 Nitro 콜백을 직접 구독하는 경로
- Q: 이 라이브러리의 큐 경로
- 핸들러: 가져온 이벤트를 처리하는 앱 코드
- 핸들러 오버: 이벤트 하나의 처리 시간을 발행 간격으로 나눈 값이며 1을 넘으면 처리가 이벤트를 따라가지 못함
- Batch: 큐에서 한 번에 가져온 이벤트 묶음
- 양보: 처리 시간 한도에 닿으면 다른 JS 작업이 실행되도록 스레드를 비우는 동작
- JS 막힘: 핸들러와 무관한 작업이 JS 스레드를 막는 시간
- JS 스레드 지연: 10ms 간격 JS 타이머가 예정보다 늦게 실행된 시간이며 최대는 가장 늦게 실행된 한 번의 지연
- 이벤트 대기 시간: 이벤트 발행 시각부터 핸들러에서 처리가 시작되는 시각까지의 시간

## 결과

- 0.1.0 구현과 0.2.0 구현을 각각 빌드해 경로 Q끼리 비교한 결과

| 플랫폼 | 지표 | 0.1.0 | 0.2.0 |
|---|---|---|---|
| iOS | 최대 JS 스레드 지연 | 10,000ms | 24.3ms |
| iOS | 이벤트 대기 시간 상위 1% | 10.9ms | 19.3ms |
| Android | 이벤트 처리량 | 171.8건/초 | 200건/초 |
| Android | 이벤트 대기 시간 상위 1% | 1,638.9ms | 0.8ms |

- 0.1.0의 iOS는 이벤트가 들어온 10,000ms 내내 처리가 이어져 이벤트 유입이 끝난 뒤에야 다른 JS 작업 실행
	- 주의: 이 값의 크기는 발행 길이에 따라 결정
- 원인
	- iOS는 JS 스레드 run loop의 CADisplayLink가 타이머를 호출하므로 신호 처리가 이어지면 타이머가 호출되지 못함
	- Android는 타이머 태스크가 신호 처리 사이에 끼어들어 막히지 않지만 양보 한 번이 다음 vsync까지 기다려 약 12ms 소요
- 프레임 단위 처리를 Android에 적용하지 않은 이유
	- Android는 프레임 한 번 안에 끝나지 않은 처리가 다음 vsync까지 밀려 핸들러 오버 0.9에서 묶음 4건(18ms)이 33ms 주기로 돌아 처리량이 약 120건/초로 감소
	- 처리 한도를 8ms로 둔 프레임 단위 처리는 iOS와 Android 모두 핸들러 오버 0.9에서 약 120건/초로 감소
- 주의: 프레임 한도 14ms와 Batch 처리 한도 8ms는 첫 시도 값

## 효과가 없거나 오히려 나쁜 조건

- 0.1.0 구현으로 B와 Q를 비교한 값이며 0.2.0 구현에서 바뀐 결과는 위 결과와 [프레임 단위 처리](frame-processing.md), [큐 용량 제한](queue-limit.md)에 기록
- 처리가 이벤트를 따라가는 조건(핸들러 오버 0.5와 0.9, 50ms 막힘)은 B와 비슷
	- iOS는 처리량이 같고 이벤트 대기 시간 중앙값 차이가 0.06ms 이내
	- Android는 일부 조합에서 Q가 B보다 악화
		- 핸들러 오버 0.9의 센서 200/s는 처리량이 200건/초에서 154건/초로 줄고 이벤트 대기 시간 상위 1%가 149ms에서 3,192ms로 악화
		- 핸들러 오버 0.5의 서버 메시지 5,000/s는 Q가 6.7%를 폐기하고 B는 폐기 없이 처리
	- Android 핸들러 오버 0.9의 Q 악화는 양보가 원인
		- Q는 양보 125\~198회에 1,296\~1,849ms를 대기하고 양보를 없앤 빌드의 Q는 처리량이 B와 같은 200건/초
		- 양보 한 번의 중앙값은 7\~10ms이고 양보 사이에 이어서 처리하는 시간은 최대 32ms
	- 주의: 양보에 처음 들어가는 계기는 확인 못함
	- 주의: 핸들러 오버 0.5의 폐기와 이벤트 대기 시간 상위 1% 악화는 다시 측정한 3회에서 재현되지 않아 원인 확인 못함
		- 서버 메시지 5,000/s는 폐기 0건이고 센서 1,000/s는 이벤트 대기 시간 상위 1%의 3회 범위가 B와 겹침
- Batch마다 고정 비용(8ms)이 드는 핸들러는 Q가 JS 타이머를 차단(iOS만 측정)
	- 센서 200/s와 1,000/s, 서버 메시지 1,000/s에서 JS 스레드 지연 상위 1%가 B 약 8ms, Q 약 10,000ms
		- Q 약 10,000ms는 이벤트가 들어온 10초 내내 타이머가 막힌 값
		- 주의: B는 이벤트를 하나씩 전달해 Batch 고정 비용을 내지 않으므로 두 경로의 조건이 같지 않음
	- Q의 양보는 0회이고 JS가 구간의 99.8% 이상 동안 핸들러를 실행
		- Batch마다 8ms가 들면 pull마다 큐가 비어 양보 조건(큐가 100ms 이상 비지 않음)에 닿지 않음
		- 양보를 없앤 빌드에서도 Q의 JS 스레드 지연은 약 10,000ms로 동일
	- 이 조합과 Android 핸들러 오버 0.9는 #30에서 플랫폼별 구현으로 해결했고 위 결과에 기록

## 측정의 한계

- 주의: 시뮬레이터와 에뮬레이터에서만 측정해 실제 앱의 JS 부하와 UI 프레임 영향은 확인 못함
- 주의: 120Hz와 저전력 모드와 실기기에서는 측정 안 함
- 주의: `subscribe`의 내부 상수는 장치에서 정하지 않음
- 주의: 센서 128B, 오디오 청크 길이, 서버 메시지의 크기 분포는 근거 자료 없이 정한 가정
- 주의: 핸들러 오버 0.5, 0.9, 1.2와 JS 막힘 50ms, 700ms, 5초는 부하 시험 관행과 Android 기준을 빌린 값이며 실제 앱이 이런 부하를 얼마나 자주 겪는지는 측정 안 함
